Systems design · Unreal Engine

A turn based combat tool

In this solo-project I have created a modular system that other developers are able to add to their existing projects to implement a turn-based battle system to their game.

My role

Tool designer

Team

1 person

Duration

8 weeks

Tools

Unreal Engine 5

Overview

The goal for this project was to break down an existing feature and create a plug-in that other users would be able to add to their projects. The main thing I focused on was modularity, I wanted users to be able to make changes so that it fits their use-case.

What I did

  • Built a custom turn-based combat plug-in
  • Researched various ways to implement features to determine which is optimal
  • Wrote the back-end logic for the various calculations taking place
  • Created the data structure that stores all the data in one place
  • Added a way to easily add custom arenas
  • Added functional battle UI

Design process

I didn't start building straight away. I researched the original first, turned that into a plan, and then built and tested the system in small steps.

  1. 01

    Research the original

    I broke down the turn-based combat of the existing game this tool is based on. A pattern analysis gave me the pattern "Time to strategize": combat pauses on the player's turn so they can weigh all their options. Game research showed how it serves both casual and competitive players by hiding mechanics like DVs and StatEXP, and I dissected its damage formula to understand what every variable does.

  2. 02

    Plan with Conditions of Satisfaction

    With many systems depending on each other, it was hard to know where to start. I turned my research into Conditions of Satisfaction, which gave me a clear goal for each week and let me finish one system at a time instead of working on everything at once.

  3. 03

    Build a consistent back-end

    Most of the logic lives in one battle manager; other blueprints only send it input. The move-select UI, for example, only tells the manager which move was picked, and the manager handles the rest. The project is split into battle logic, data and UI folders, with Perforce for version control and regular builds to keep it stable.

  4. 04

    Playtest and iterate

    To show how the system can be used, I built a demo level where different creatures, moves and types interact. I ran two playtest sessions, watching others play through it, and used the feedback to balance both the level and the system, ending up with three versions of the demo level.

Challenges & what I learned

The biggest challenge was scope. Recreating every battle mechanic would have been far too much, so I had to decide what to cut without losing the player experience. My research made those calls easier: StatEXP and DVs make every creature feel unique, but without a catching or switching system they can't shine, so they were easy to cut. The playtest results told me I cut the right things.

I also had to change what I was building. I set out to make a complete tool that others could pick up and use, but down-scoping and time constraints pushed me towards a strong foundation that others can build on. I wrote tech research and a how-to document to support that direction, and when others worked with the project they understood how it functioned and got excited to create new content.

This project taught me as much about scope management and knowing when to change direction as it did about the technical implementation.
